# README 五问

README 的唯一职责：让目标读者在 5 分钟内决定"用不用"并跑起来。五问框架适用于一切说明书型文档（项目 README、工具说明书、部署手册）；技术报告用末节"降维用法"。

## 五问框架总表

| # | 问 | 读者心里的话 | 回答载体 | 缺席后果 |
|---|-----|------------|---------|---------|
| 1 | 是什么 | 这东西解决什么问题 | 一句话定义 + 做什么/不做什么边界 | 首屏 10 秒关页 |
| 2 | 给谁用 | 是不是我该用的 | 目标画像 + 前置条件 | 错误用户涌入，issue 爆炸 |
| 3 | 怎么跑起来 | 最快多久能试一下 | 编号步骤 + 可复制命令 | 想试的人折腾不动，流失 |
| 4 | 怎么验证跑通了 | 我这算成功了吗 | 验收命令 + 预期输出成对 | 用户卡在"好像成功了" |
| 5 | 坏了找谁 | 出问题有人管吗 | issue 入口 + 报错对照表 + 响应预期 | 静默弃用，不会再来 |

## 逐问正反例

### 问 1：是什么

- 反例：本项目是一个强大而优雅的现代工具，致力于全方位提升开发体验。
  - 病：全是形容词，读完不知道它能执行什么动作。
- 正例：把 Markdown 表格批量转成 Excel 的 CLI 工具，支持管道输入；不做图表渲染和公式转换。
  - 法：动词开头说能力，紧跟一句"不做什么"划边界。边界句与能力句同等重要——README 一半的噪音来自没写边界。

### 问 2：给谁用

- 反例：适合所有开发者使用。
  - 病："所有人"等于没人，用户无法完成自我匹配。
- 正例：给每周写内部周报的工程师；需要会命令行、Python >= 3.10.12；不需要懂 pandoc。
  - 法：画像（谁 + 什么场景）+ 会什么（前置技能/环境）+ 不需要会什么（降门槛承诺）。

### 问 3：怎么跑起来

- 反例：安装依赖后即可使用。
  - 病：依赖从哪装、装到哪、怎么确认装上了，全没写。
- 正例：

  ```bash
  git clone https://github.com/<org>/<repo>.git
  cd <repo> && pip install -e .   # 预计 1 分钟
  techdoc --version               # 输出 2.1.0 即成功
  ```

  - 法：命令按顺序可整块复制；每步带成功标志或预期耗时；有平台分支（macOS/Linux/Windows 差异）时拆小节。

### 问 4：怎么验证跑通了

- 反例：运行 demo.py 就能看到效果。
  - 病：什么效果、什么算对，全靠用户猜。
- 正例：

  ```text
  $ techdoc check --demo
  [OK] 模板渲染 3/3 通过
  ```

  - 法：命令与预期输出必须成对出现，预期输出原样贴，不改写不概括。这是全篇最值钱的一对信息。

### 问 5：坏了找谁

- 反例：欢迎联系作者。（或整节缺失）
  - 病：没有入口、没有时效预期，用户只能弃用。
- 正例：

  | 症状 | 原因 | 处理 |
  |------|------|------|
  | `command not found` | PATH 未包含安装目录 | 见安装节第 3 步 |
  | 渲染中文乱码 | 缺少 Noto 字体 | `apt install fonts-noto-cjk` |

  另提 issue 走模板（附链接），工作日 48 小时内响应；安全漏洞走 security.md，勿提公开 issue。
  - 法：常见报错做成"症状/原因/处理"对照表，比 FAQ 段落检索快得多；响应预期写成可核对的承诺。

## 结构模板（按需取用）

### 首屏：badge 行 + 一句话

```markdown
![CI](https://github.com/<org>/<repo>/actions/workflows/ci.yml/badge.svg) ![License](https://img.shields.io/badge/license-MIT-blue) ![Version](https://img.shields.io/badge/v-2.1.0-green)
一句话定义：动词开头，不超过 30 字
```

- badge 只放活的（CI、license、版本）；连续 30 天不更新的 badge 删除。死 badge 比没有 badge 更减分。

### 三问三答表（首屏摘要）

| 问题 | 答案 |
|------|------|
| 给谁用 | 每周写周报的工程师，会命令行即可 |
| 怎么跑 | 三条命令，见"快速开始"节 |
| 怎么验证 | `techdoc check --demo`，见"验证"节 |

### 方法论折叠（details）

设计取舍、竞品对比、性能数据放 `<details><summary>为什么这样设计</summary>…</details>`：首屏不占篇幅，想深究的人自己展开。

### 结构树

```text
<repo>/
├── src/   # 核心逻辑
├── docs/  # 文档
└── tests/ # pytest 用例
```

- 只列读者需要理解的目录，每个目录一行注释说职责；不逐文件罗列。

### Roadmap 勾选框

```markdown
## Roadmap
- [x] v2.1.0（2026-09-30）管道输入
- [ ] v2.2 Windows 原生支持（2026 Q4）
```

- 完成即勾并补日期；连续两个版本未动的条目删除。过期的 Roadmap 是负资产。

### 致谢差异表（fork 必备）

| 项 | 上游 | 本 fork |
|----|------|---------|
| 定位 | 通用格式转换 | 只保留 Excel 输出，速度快 3 倍（2026-10-08 压测） |
| 改动 | — | 重写渲染器（见 docs/adr/007-渲染器重写.md） |

- fork 不写差异表，读者就无法判断该用哪个；"为什么不合回上游"必须一句话说清。

## 排版规则表（争议以此裁决）

| 规则 | 要求 | 违例处理 |
|------|------|---------|
| 标题层级 | 每文件唯一 h1；从 h2 起步不跳级 | 出现 h2→h4 直接改为连续 |
| 表格规模 | ≤5 列；单元格超过 40 字 | 拆表、转列表或转段落 |
| 代码块语言 | 每块必标语言；输出、目录树用 text | 未标注视为未完成 |
| emoji | 只允许用于节标题导航锚点，全文不超过 3 处 | 正文 emoji 全删 |
| 列表嵌套 | 不超过 2 层 | 第 3 层改成小节或表格 |
| 并列句式 | 同一列表内各项句式一致 | 统一为动词开头或名词短语 |
| 空行 | 段间 1 空行；标题前后各 1 空行 | 防渲染器差异 |

## 降维用法（技术报告/交付说明书）

五问压成三问：是什么（含边界与适用范围）、怎么用（步骤 + 验收标准）、坏了找谁（支持渠道与响应预期）。"给谁用"并入"是什么"：报告类文档的读者由交付对象指定，无需画像。"怎么验证"并入"怎么用"：交付说明的每一步都要带验收标准，验收不过即步骤没写完。
