# code-quality：开发与代码质量

**一句话定位**：把「这段代码能不能安全合入」拆成可执行的检查动作——评审按优先级找真问题、测试先红后绿、重构小步可回退、性能先测量再动手，所有结论落表。

## 执行纪律（违反任一条＝本次产出作废重做）

| # | 纪律 | 违反长什么样 |
|---|---|---|
| 1 | 评审先看接口契约再看实现 | 没核对函数签名/出入参/错误码含义，直接跳进函数体挑命名 |
| 2 | 测试先红后绿 | 没亲眼见测试失败（红）就写实现；或实现写完再补测试装绿 |
| 3 | 重构小步提交 | 一次提交里「改结构」和「改行为」混在一起；无测试覆盖就大改 |
| 4 | 性能先测量再优化 | 没有基准数据（耗时/内存/QPS）就凭感觉改；改完不复测对比 |
| 5 | 风格交给机器 | 把缩进/引号/import 顺序当人工评审意见写进表 |
| 6 | 意见必须分级 | 只说「这里不太好」，不带 级别/位置/依据/改法 四要素 |
| 7 | 测试红了先疑测试 | 实现没动、测试突然红，不查测试环境直接改实现迁就 |

## 产物约定（四类产物，全部先落表）

1. 评审 → **评审意见表**（列固定，口径见 review-handbook.md §2/§3）：

| 级别 | 位置 | 问题 | 依据问句 | 建议改法 |
|---|---|---|---|---|
| 必须改/建议/疑问 | 文件:行 或 函数名 | 一句话说清 | 评审手册 §4 编号 | 给方向，不贴大段代码 |

2. 测试 → **测试清单表**：用例名 | 输入（标注边界值来源）| 期望 | 层级。
3. 重构 → **提交序列**：每步一行 = 手法名 + 范围 + 改后跑哪组测试。
4. 性能 → **前后对比表**：指标 | 改前 | 改后 | 数据来源（命令/环境）。

表外解释 ≤3 句；表里填不出来的结论不许下。

## 开局流程（接到评审/测试/重构任务，前 30 秒）

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | 判类型：评审 / 测试 / 重构 / 性能 / 技术债，五选一 | 说出是哪类 |
| 2 | 按必读短表打开对应文件的对应节 | 只引用节号，不复述全文 |
| 3 | 评审类先跑 评审手册 §1 动作序列；测试类先定层级（测试与重构 §1）；重构类先查测试覆盖 | 一句开局结论 |
| 4 | 做完落对应产物表 | 表 |

## 常见坑（自查，出现即返工）

| 坑 | 正确做法 |
|---|---|
| 评审意见全是风格问题，没有正确性/安全 | 回 评审手册 §1 按优先级重扫一遍 |
| 写测试只为凑覆盖率数字 | 按 测试与重构 §3 边界值挑输入；覆盖率是副产品 |
| 重构一次提交混了多个手法/还改了行为 | 拆提交：一提交一手法，改行为单独提交 |
| 性能优化只有改动没有前后数据 | 补基准测量；没数据不下「变快了」的结论 |
| 把「疑问」当「必须改」压作者 | 按 评审手册 §2 口径重新分级 |
| mock 一切导致测试只测了 mock | 回 测试与重构 §4 分寸线自查 |

## 边界（什么时候不是本技能的活）

| 情况 | 转交 |
|---|---|
| 只想跑 formatter/lint，无人工判断 | 直接执行工具，不进知识库 |
| 专门做 0day/渗透式安全审计 | 走 secure-code-audit；本技能只在评审 §1 优先级 2 做常规安全检查 |
| 架构选型/技术方案对比 | 不在本技能范围，按普通设计讨论处理 |

触发后 30 秒内说清：本次属于 评审/测试/重构/性能/技术债 哪一类、按短表开了哪个文件哪一节。
