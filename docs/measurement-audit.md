# 评分与对照审计

审计日期：2026-10-29。对象是本地工作区的 `tools/bench.py`、原始运行/判分以及 `site/data.json`；工作区的运行数据与公开 Git 快照可能不同，以下数量不能当作公开发布批次规模。

现有数据足以展示带技能运行的评分分布，但大部分技能缺少裸跑和无关材料对照，尚不能回答“技能带来多少增益”或“新模型是否已替代它”。新工具先报告证据覆盖，不用高绝对分填补缺失基线。

## 发现与处理

| 问题 | 实现证据与影响 | 此次处理 |
|---|---|---|
| 跨模式权重不同 | `WEIGHTS` 中 M1 使用正确性/完整性/表达清晰 = .55/.30/.15；M2/M4 使用 .40/.25/.20/.15，其中 .20 是技能遵循。M4 的技能遵循为 null 时，`weighted()` 又对其余 .80 归一化。因此旧总分直接相减不是统一质量指标。 | 新工具逐判官统一按 .55/.30/.15 重算；技能遵循和历史总分只列诊断，不进增益。 |
| 重复试验可能被覆盖 | `cmd_agg()` 的 `totals` 键为 `(model, task, mode)`，不含 trial；多试验对同一任务的增益会按遍历顺序覆盖。映射表本身也未保存 trial。 | 从原始产物 frontmatter 读取试验号，按 skill/model/task/trial/mode 对齐，重复键列异常并整格排除。 |
| 判官池不一致 | 独立汇总两个模式后作差，可能把判官更替混入模式差异。 | 每一对只使用两模式共有的外部判官；默认至少两个判官家族；家族内均值、家族间中位数。自评不进入结果。 |
| 极少数技能有基线 | 本地 2,652 个映射文件共含 M2=9,723、M1=16、M4=15、M3=16 条。通过公共维度/身份核验后的 M2=9,719；只有 humanizer 的四个模型组合同时有两类对照观测。 | M2-only 结果明确标 `insufficient_evidence`，不输出有效/无效或退役判断。 |
| 对照不支持“纯内容增益” | M4 材料从其他技能截取；没有持久化的等 token 验证、无关性验证以及多种材料敏感性分析。 | Δ24 仅称“M2 相对该 M4 材料的差值”；解释保留材料内容、干扰及 token 差异。 |
| 同试验号不等于严格可复现 | 原始元数据含模型标识和试验号，却未锁定服务端模型版本、任务/技能哈希、工具/环境版本或采样种子。 | 现有重算只叫“配对观测”；未来重跑应保存完整 manifest，不能把它解释成严格因果估计或最新版模型结论。 |
| 总分对缺失指标给默认分 | `SkillScore` 没有 M3 时给 10/20 触发分；任务间标准差被用于“稳定性”，不等于同任务重复运行稳定性。 | 新工具不使用 SkillScore 作增益或退役决策；重复运行波动仅在同任务内计算。 |

## 可运行工具

`tools/value_audit.py` 仅依赖 Python 标准库；不导入批跑器，不联网，不调用模型，不修改运行数据。默认向 stdout 输出，只有 `--output` 才写文件。`--root` 默认从脚本位置解析仓库根目录。

公开 clone 的 `site/data.json` 足以进行证据覆盖检查：

```bash
python3 tools/value_audit.py --site-data site/data.json --skills humanizer --format markdown
python3 tools/value_audit.py --site-data site/data.json --skills humanizer
python3 tools/value_audit.py --site-data site/data.json --output /tmp/skillfit-coverage.json
```

快照模式统计聚合行的模式数量与同模型/同任务的“候选任务对”。聚合数据缺少逐判官评分、trial 和原始运行状态，工具不会恢复或相减旧 `gains`、历史总分、维度中位数；所有组合均标 `insufficient_evidence`。候选对数不能当作通过审计的配对样本数。

本地保留 `scoring/<skill>/映射表.json`、逐判官 JSON 和映射所指向的 `runs/` 原始 Markdown 时：

```bash
python3 tools/value_audit.py --root . --skills humanizer --format markdown
python3 tools/value_audit.py --root . --skills humanizer --output /tmp/skillfit-value-audit.json
```

旧映射中的 `结果/` 可对应工作区重命名后的 `runs/`。每次仍核对产物 frontmatter 的技能、模型、任务、模式、试验号与 `状态: ok`。这解决目录迁移，不构成文件内容未变的密码学证明。

原始评分模式逐格验证公共维度是有限的 0–5 数值，拒绝布尔值、字符串、NaN、越界和缺项；排除自评、无效判分、重复判官和重复 task/trial/mode；共有判官不足时不作差。模型 ID 严格匹配，包含 `@api` 路由，不把不同路由或版本合并。

输出保留每个 task/trial 的分数、差值及共有判官；先在每个任务内平均 trial 差值，再对任务等权平均。同任务有至少两次配对运行时给样本标准差和范围。单次运行标准差为 null；不把判官票、不同任务或不同模型当成同一独立试验，不输出缺乏抽样依据的总体置信区间。

完整原始扫描得到 9,711 个映射技能×模型组合，9,707 个存在可用公共维度评分，只有上述 4 个组合同时有两种对照。发现 28 份无效公共维度判分，以及 OfficeCLI__iOfficeAI 下 4 处映射身份不一致，均跳过。异常计数表示数据校验问题，不等于失败任务数。

同一工作区当时的 `site/data.json` 包含 2,652 个技能和 9,719 条 M2 聚合行，M1=16、M4=15、M3=16。快照生成时间是网站导出时间，不能当作这些模型任务的重新运行时间。工具会从传入文件重新统计，避免把本报告数字固化为项目徽章。

## 如何判断模型升级是否替代技能

应在相同任务集合与验收器上，对旧模型、新模型分别重新运行 M1/M2/M4，锁定任务、技能、模型服务版本和工具环境；比较新模型自身的配对增益，而不是比较“新模型 M1”与“旧模型 M2”的绝对分。后者同时改变了模型和技能条件。

“无法观察到显著差异”也不证明等效。开始实验前需定义任务可接受误差、实际价值阈值、预算/耗时上限以及失败率上限，用足够的同任务重复运行估计不确定性。只有新模型技能增益落在预先定义的实用等效范围内，且移除技能后的验收、成本、工具行为与私有约束都满足要求，才进入人工复核的退役候选。现有运行数据缺少成本、token、可靠版本指纹和重复运行，不支持自动化退役结论。
