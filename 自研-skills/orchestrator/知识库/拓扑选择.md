# 拓扑选择（拆分前必读）

本篇解决三个问题：选哪种并行拓扑、并发开多少、任务挂了/拖尾了怎么办。
入口：SKILL.md 短表 §1/§2/§3/§4/§5 各行。

## §1 拓扑判定表

判定三问（按序回答，答案直接查表）：
1. **依赖数**：子任务间有几条「A 完成才能做 B」的边？（0 / 成链 / 混合）
2. **写冲突**：是否有 ≥2 个子任务要写同一个文件？（有 / 无）
3. **上下文体量**：单个子任务的输入＋产出能否装进一个 subagent 上下文？（能 / 不能）

| 拓扑 | 依赖数 | 写冲突 | 体量 | 判定特征 | 典型场景 | 主要风险 |
|------|--------|--------|------|----------|----------|----------|
| 单 agent 直做 | 任务仅 1 个 | — | 小 | 拆分开销 > 任务本身 | 单文件小改、读一文件答一问 | 过度拆分反而慢 |
| 流水线 pipeline | 成链 A→B→C | 各步产物不同 | 各步装得下 | 后一步吃前一步的产物 | 提取 → 分析 → 成文 | 本身无并行收益，别硬拆步 |
| fan-out 扇出 | 0 | 无 | 各自装得下 | N 个异构独立目标 | 3 个模块各审各的、10 个文件各自提炼 | 漏查隐藏写冲突 → 覆盖 |
| map-reduce | 片内 0 | 各片产物不同 | 单片装得下 | 同构任务 × 大量输入 | 100 份文件批量摘要、50 个目标逐个探测 | 分片不均 → 长尾 |
| 递归拆分 | 任意 | 合并层统一管 | 单任务装不下 | 输入太大 / 目标太泛 | 全仓库审计按目录再拆 | 超 2 层失控、中间产物无人收 |

**判定顺序**：
- 依赖 0 → 异构目标 = fan-out；同构 × 量多 = map-reduce
- 依赖成链 → 流水线；链中相邻几步各自独立完成的，升级成分层 DAG（§2）
- 混合依赖（部分独立 + 部分成链）→ 分层 DAG
- 单子任务装不下 → 先递归拆一层，子片再套前四种
- 写冲突「有」→ 无论选哪种拓扑，冲突文件一律合并归属单一写者（见 prompt工程.md §5）

判定实例（30 秒走完）：
```
任务：审计 A/B/C 三个模块（互不相干），再写一份汇总报告，其中 A 模块代码量是 B/C 之和十倍
三问：依赖＝审计三者独立、汇总依赖三者（混合）→ 分层 DAG
     写冲突＝三份审计产物不同文件，无冲突
     体量＝A 装不下 → A 先递归拆成 A1/A2/A3
结论：L0 并行下发 A1/A2/A3/B/C（5 个），L1 汇总报告等 L0 产物落盘后下发
```

反模式（查到即纠正）：

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| 万物皆 fan-out | 有依赖的任务也被并行，B 拿到 A 的半成品 | 先画 DAG 再下发 |
| 拆太碎 | 每个 subagent 只干 30 秒的活，调度开销过半 | 合并粒度：单 subagent 5-10 分钟 |
| 主线程亲力亲为 | 只并行了 2 个，剩下的自己闷头干 | 主线程只编排 |
| 层数失控 | 递归拆到 3 层以上，中间产物没人管 | 最多 2 层，再大就按 §3 降并发排队 |

## §2 DAG 构建法（三步成图）

**Step 1 列子任务**：把任务穷举成清单，每条一行动词开头（「审计 X」「提炼 Y」「比对 Z」）。
**Step 2 标依赖**：每条后面标「依赖：无 / 依赖 #i」；只认真实数据流（B 要读 A 的产物才有边），行政先后顺序不算依赖。
**Step 3 分层**：按依赖深度分层——无边 = L0；只依赖 L0 = L1；依此类推。

分层后的下发规则：

| 层 | 下发方式 |
|----|----------|
| L0（无依赖） | 同一轮全部并行下发，数量只受 §3 并行度封顶 |
| Ln（n≥1） | 等 Ln-1 **产物落盘并验收**后再下发；prompt 里直接给上游产物绝对路径 |
| 层内任务 | 默认全并行；层内出现互相依赖 = 上一步标错了，挪层 |

文本 DAG 示例（10 行内画完）：
```
任务：审计 3 个模块 + 汇总报告
L0: 审计模块A ┐
L0: 审计模块B ├─ 三者无依赖，同轮并行
L0: 审计模块C ┘
L1: 汇总报告 ← 依赖 L0 三份审计报告路径（/out/A.md /out/B.md /out/C.md）
```

画完自查两条硬标准：
1. 同层任务两两无数据依赖（有 → 挪到下一层）
2. 每条边都对应一个真实产物路径（没有 → 删边改并行）

中途改图：用户追加需求或某任务降级时，只重画受影响分支，已 done 的子任务不动，增量下发新差量。

## §3 并行度定法（三类瓶颈）

| 瓶颈类型 | 识别信号 | 并行度公式 | 典型值 |
|----------|----------|-----------|--------|
| IO 密集（读文件/爬网页/下载） | CPU 闲、大量时间在等网络/磁盘 | ≈ 目标数，仅受下一类限流封顶 | 8-16 |
| CPU 密集（解析/计算/压缩） | CPU 打满、进程各吃一核 | ≈ 核数 × 1.2 | 4-8 |
| API 限流（LLM 调用/目标站点） | 429、限流报文、超时率上升 | = 限流窗口内允许请求数 × 0.8（留余量） | 按响应头算 |

执行规则：
- 先判瓶颈类型再定数；混合型取各瓶颈计算结果的最小值
- 运行中触发限流（429 或超时率 >20%）：并行度立即减半，只减不弃
- 任务数 ≠ 并行度：任务多于上限的进台账排队（queued），有空位就补
- 任何情况不为省 token 降并发——并发只由瓶颈决定

## §4 失败处置（四级阈值表）

| 级别 | 触发条件 | 动作 | 示例 |
|------|----------|------|------|
| 1 重试 | 首次失败且报错可读（超时/瞬时 5xx/网络抖动） | 原样重发 1 次，prompt 不动 | 单次请求超时 |
| 2 切片 | 重试再败，或单任务耗时 > 均值 2 倍 | 按 §5 公式拆成 2-4 片并行重发 | 大文件解析超时 |
| 3 降级 | 切片仍败，或环境缺依赖装不上 | 换工具/换模型/砍精度（全量→抽样），台账记「降级+原因」 | 某库装不上 → 换标准库实现 |
| 4 放弃 | 降级也败，且该子任务不在关键路径 | 标 skipped＋原因，进「需人工确认」，不阻塞其余聚合 | 边缘配置项解析 |

硬规则：
- 同一任务连续失败 2 次 → 必须换方式（切片或降级），**禁止原样第 3 次重试**
- 放弃只允许非关键路径；关键路径挂了 → 回 §1 重新拆分整个分支
- 每次失败都写台账：`时间 | 任务ID | 级别 | 报错摘要 | 下一步`，验收时汇入「失败或跳过项」

## §5 长尾任务再拆分公式

监控时算三个数：`T_avg` = 已完成任务平均耗时；`T_run` = 在跑任务已耗时；`N_left` = 该任务剩余量估计。

**拆分判据（满足即拆）**：
```
T_run > 2 × T_avg  且  N_left 可独立切分（无中间状态依赖）
```

拆法（按序选第一个命中的）：

| 情形 | 拆法 |
|------|------|
| 输入可切（多文件/多条目/多目标） | 按输入对半切成 2-4 片并行重发；原任务停掉，已完成部分保留落盘复用 |
| 输入不可切但阶段可切 | 按阶段切：已完成阶段的产物先落盘，剩余阶段单独下发并传产物路径 |
| 都不可切 | 不拆，转 §4 级别 3 降级；再不行标长任务后台跑完等通知 |

拆分后动作：新片进台账并继承原任务 ID（T3 → T3a/T3b），原任务标 superseded，避免重复计数与漏算。

两条禁止：长尾任务放着干等不许；未达判据乱拆也不许（拆分本身有调度开销）。
